# DBForge V0.6 — index strategy experiment

## Research question

Does creating an index on only the determinant column actually accelerate V0.5's exact grouped functional-dependency check, or does it introduce costly table lookups for the dependent columns?

The competing execution paths were:

1. **No index:** scan the staging table and let SQLite use a temporary B-tree for GROUP BY.
2. **Determinant-only index:** scan an index ordered by the determinant, then fetch dependent values from the table.
3. **Covering index:** scan an index containing the determinant and all dependent columns needed by that grouped check.

## Method

Three synthetic one-million-row layouts were generated by generate_index_benchmark_data.py and tested:

- **Random orders:** 1,000,000 rows; customer and product determinants have different cardinalities; input order is randomized.
- **High-cardinality orders:** 1,000,000 rows; customer key cardinality is approximately 500,000 and product key cardinality approximately 333,000.
- **Customer-sorted orders:** 999,990 rows; rows are ordered by customer ID while product IDs remain randomized.

Each dataset had two determinant scans: customer_id -> customer_name, region and product_id -> product_name, category. Each strategy ran twice against fresh copies of the same disk-staged SQLite input. Strategy order was randomized between repetitions. The reported microbenchmark total is the sum of index-build time and grouped-query time for both scans; CSV ingestion and initial staging are excluded.

Environment: Python 3.13.5, SQLite 3.46.1, Linux x86_64, 4 GiB cgroup memory limit. SQLite cache target was 8 MiB, temp_store=FILE, and mmap_size=0. Query plans were captured with EXPLAIN QUERY PLAN.

## Results: exact grouped scans

| Workload | No index | Determinant-only | Covering index | Fastest |
|---|---:|---:|---:|---|
| Random orders, 1M | 1.260 s | 3.675 s | 1.736 s | No index |
| High cardinality, 1M | 1.534 s | 4.296 s | 1.967 s | No index |
| Customer sorted, 999,990 | 1.002 s | 2.240 s | 1.601 s | No index |

The determinant-only index was approximately 2.9x, 2.8x, and 2.2x slower than no index respectively. This repeated across randomized, high-cardinality, and partially sorted inputs, so the result is not explained by one input order alone.

The query plans explain the trade-off:

- No index: SCAN raw followed by USE TEMP B-TREE FOR GROUP BY.
- Determinant-only: SCAN raw USING INDEX; dependent columns require table lookups.
- Covering: SCAN raw USING COVERING INDEX; dependent values can be read from the index without looking back into the table.

Covering indexes reduced grouped-query time substantially, but their construction cost outweighed the query savings in these tests. In the random-order workload, a determinant-only index occupied about 17.1 MB per scan, while the covering indexes occupied about 58.1 MB and 66.3 MB. The covering path was consistently faster at query time, but not fastest when build time was included.

The grouped result tuples were identical across all three strategies for every workload.

## Results: full pipeline across input sizes

| Rows | V0.5 median | V0.6 no-index median | Change | V0.5 analysis | V0.6 analysis |
|---:|---:|---:|---:|---:|---:|
| 20,000 | 0.262 s | 0.248 s | 5.3% faster | 0.092 s | 0.089 s |
| 100,000 | 1.488 s | 1.497 s | 0.6% slower | 0.590 s | 0.563 s |
| 250,000 | 4.092 s | 3.484 s | 14.9% faster | 1.752 s | 1.276 s |
| 1,000,000 | 16.786 s | 15.198 s | 9.5% faster | 7.392 s | 5.085 s |

The 20k, 100k, and 250k cases and the 1M case each used two runs per compared mode. At 100k rows, total time was effectively tied (V0.6 was 0.6% slower), despite a lower analysis time; this is a reminder that the change is not a universal end-to-end speedup. At 250k and 1M rows, the analysis savings were large enough to improve total time. Peak RSS remained around 103 MiB at 20k and 116–117 MiB for larger inputs, with no material memory change from V0.5.

Both V0.6 no-index 1M runs processed 1,000,000 rows and passed exact reconstruction verification. Full-pipeline results for all sizes are in benchmark_full_pipeline_results.json.

For context, one full-pipeline V0.6 covering-index run took 15.81 s, with 6.13 s in analysis and 2.00 s spent building indexes. One determinant-index run took 16.93 s, with 7.54 s in analysis. These are single-run diagnostics, not statistically robust comparisons; the two-run index microbenchmarks above are the stronger evidence for the access-path choice.

## Decision

V0.6 defaults to no index for exact determinant-group validation. The determinant-only index is retained as an explicit diagnostic option so that future workloads can challenge this decision. The covering-index option is also retained for controlled testing, but it is not the default because index-build time and storage outweighed its faster query execution in the tested cases.

This is a measured execution-plan improvement, not a new FD discovery algorithm. The results do not establish that no-index is optimal for every schema, device, or SQLite version.

## Remaining uncertainty and next experiments

- Very wide dependent strings and a large number of candidate RHS columns may change covering-index economics.
- Slow disks or network filesystems may alter the cost of SQLite's temporary GROUP BY B-tree.
- Windows and other SQLite versions have not been tested.
- Real customer datasets have not been tested; synthetic cardinality patterns are only proxies.
